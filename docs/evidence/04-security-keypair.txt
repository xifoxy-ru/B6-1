B6-1-011 보안그룹·SSH 키 페어 증빙 — 최초 실패 후 승인된 복구 완료

실제 UTC/안전한 CLI 인자·최소 결과는 04-security-keypair.json에 기록했다.
리전 ap-northeast-2, 프로필 b6-1-iam. 공식 aws login은 사용자 Incognito 인증·동의 후 실제 exit0. 이후 STS에서 기대 IAM 사용자·계정 일치를 메모리에서 검증하고 계정/ARN을 마스킹했다.

보안그룹: sg-030553cbc06d587a7 / b6-1-web-sg / vpc-010aff9ac6af6adce.
태그 Project=B6-1, Name=b6-1-web-sg. 인바운드 정확히 TCP80 0.0.0.0/0 및 TCP22 PUBLIC_IPV4_MASKED/32. 기본 IPv4 전체 아웃바운드를 유지했다. SG 생성과 ingress 각각 동일 인자의 DryRunOperation 후 실제 한 번 실행했다.
checkip.amazonaws.com은 검증된 TLS와 --noproxy * 직접 요청으로 global IPv4를 메모리에서 파싱했다. ingress 직전 및 최종 현재 IP 일치를 검사했고 원시 IP나 IP 해시를 저장하지 않았다. 복구 중 SG는 변경하지 않았다.

트러블슈팅 기록
증상: 최초 CreateKeyPair는 성공했으나 개인키 파일이 비어 있어 사용할 수 없었다.
가설: 생성 API 실패가 아니라 로컬 응답 처리 순서가 개인키 저장을 막았을 수 있다.
검증: CreateKeyPair exit0 이후 sanitizer가 응답에 없는 KeyType을 읽어 KeyError 발생. 공식 응답 계약과 targeted DescribeKeyPairs로 cloud key key-05300d9117474bf5e 존재를 확인했다. 로컬 파일은 regular/no-symlink/size0/0600/ignored였으며 해당 키 참조 인스턴스는 0개였다.
조치: 원실패/코드를 보존하고 KeyMaterial write·fsync를 optional metadata 처리보다 먼저 수행하도록 수정했다. 실제 키가 아닌 메모리 fixture로 KeyType 없음·optional 필드 없음·부분 write/InterruptedError/일시 write·fsync 실패를 검증하고 독립 pre-recovery PASS를 받았다. 사용자가 해당 cloud key와 이번 빈 파일만 삭제 후 재생성을 명시 승인했다.
복구 실행: fresh STS/정확 old key ID·이름·type·태그·fingerprint/참조0/local inode·owner·empty·mode·ignore guard를 다시 확인했다. exact key ID DryRunOperation→삭제 한 번→absence 조회 확인 후 자기 빈 파일만 제거하고 새 exclusive/no-follow0600 descriptor를 열었다. 동일 b6-1-ssh-key/ed25519/태그로 DryRunOperation→생성 한 번 실행했다.
결과: 새 key key-00e758429d0610364. 개인키 직접 write·fsync 완료 후 메타데이터를 기록했다. DescribeKeyPairs 공개키와 ssh-keygen -y 결과를 메모리에서만 비교해 대응 PASS, 파일 regular/nonempty/owner0600·디렉터리0700·Git ignored를 확인했다. 이전 key ID는 삭제됐으며 새 키가 현재 사용 대상이다.
예방: 필수 KeyMaterial을 먼저 durable 저장하고 응답 optional 필드에 의존하지 않는다. transient write/fsync 오류는 같은 descriptor·메모리에 payload를 보존해 처리하며 cloud create를 반복하지 않는다. 프로세스/호스트 강제 손실 시 메모리 보존을 보장할 수 없다는 한계는 남는다.

개인키/공개키 material 또는 material digest는 로그·증빙·스크립트·Git에 넣지 않았다.

수동 안내: 개인키는 로컬에 비공개 보관하고 채팅/메일/Git에 공유하지 않는다. 이 단계에 추가 수동 조작은 없다. EC2와 실제 SSH 연결은 별도 승인 단계이며 아직 실행하지 않았다. 공인 IP가 바뀌면 SSH /32 변경 승인을 요청하고 전체 IP로 넓히지 않는다. 삭제 권한은 이번 복구 exact old key/빈 파일에만 적용했고 다른 자원 삭제는 하지 않았다.
스크린샷/EC2/SSH/HTTP/outbound curl 검증은 미실행이다.
